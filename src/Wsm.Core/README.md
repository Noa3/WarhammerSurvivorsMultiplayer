# Wsm.Core

This is a managed session library, not a game mod or gameplay integration. No native/IL2CPP gameplay adapter, actual world capture/application, XP source, progression thresholds, bot execution, or game upgrade validation is implemented. DTOs are a generic boundary, not representations verified against Warhammer Survivors. Lobby readiness, hero/weapon selection and host-start orchestration are not implemented; clients must run their own local game instances, not stream the host game.

## Launcher integration

Reference `Wsm.Core.csproj` from a .NET 10 application. Create `new SessionHost(new SessionSettings(maxClients, deathMode, botCount, botDifficulty), password, port)` and call `Start()`. The bind address defaults to IPv4 loopback; pass `bindAddress: IPAddress.Any` or a selected local interface explicitly for LAN. `Port` exposes the assigned port. No firewall or forwarding changes are made.

Join with `await SessionClient.ConnectAsync(address, port, password, cancellationToken)`. Its server-assigned `PlayerId` and immutable `Settings` identify the session. Drain host `Joined`, `Disconnected`, and `Commands`; use `ConnectedPlayerIds` to reconcile state. Notifications are bounded best-effort (128); drain promptly, since overflow drops notifications. Commands already queued can outlive a disconnected player: check current membership when consuming them. Commands are bounded to 128; a sender is disconnected if the queue is full. For each host snapshot, call `PublishSnapshotAsync(new WorldSnapshot(tick, entities), token)`; clients drain `Snapshots` (16, oldest dropped on overflow). Publishing validates and serializes once, rejects an encoded JSON frame above 262,144 bytes even with no clients, then enqueues the same immutable bytes per peer. Each peer has at most one in-flight frame and one pending latest snapshot, in addition to its bounded reward control queue; intermediate snapshots may be dropped. Completion means enqueued, not delivered. Cancellation is checked before fan-out, not after enqueue; slow peer writes time out after 30 seconds, and failed writes close only that peer immediately. A canceled or failed write closes its connection once writing begins to protect framing. A cancellation while waiting for the send lock does not close it. Only the host can publish snapshots; malformed or unauthorized client messages disconnect their sender. A malformed host message completes the client's snapshot channel with a protocol error.

Clients call `SendInputAsync` and `SendUpgradeAsync` for their own `PlayerId`. The host checks identity and shape, not actual game legality, XP thresholds or upgrade eligibility. The future gameplay adapter must perform those checks and decide how to apply these commands. `SessionState` supplies independent death-policy bookkeeping; its caller must add/remove participants, report deaths, and apply the resulting game behavior. `BotPolicy.Move` returns a deterministic bounded direction; the host/adapter must create bots and apply their inputs.

## Authoritative encounter and finalized private rewards

The host's trusted game adapter calls `host.Encounter.RegisterEnemy(id, maxHp)` once per unique stable ID and `ApplyValidatedHit(hitId, enemyId, damage)` only after validating a real hit. The latter returns true exactly on the death transition; duplicate hit IDs are ignored. State is locked and capped at 2,048 enemies and 100,000 unique hit receipts; capacity fails closed, with no eviction or reset. An additional exact JSON byte budget reserves room for all admitted health records in an otherwise empty snapshot at the largest tick and initial HP. It rejects an enemy before mutation if its encoded ID and HP would exceed the 262,144-byte frame. Therefore long or heavily escaped IDs can cause admission to fail well before 2,048; even admitted health state plus caller entities may exceed the frame and such publication fails without changing the accepted tick. This API does not validate physics, create game enemies, or wire hits to a real game. `PublishSnapshotAsync` attaches a copy of this state as `Enemies`; callers must leave that property empty. `WorldEntity` remains generic, and the adapter must correlate IDs and apply health/death to actual game objects. Snapshot delivery is replaceable; a death transition is not an individual guaranteed event.

`SessionSettings.Policy` is the shared `Wsm.Contracts.CoopPolicy`, defaults to personal XP and pickups, is required in protocol-v4 JSON, and is validated by host and client. For a collection finalized by trusted game logic, call `host.PublishReward(collectorId, new RewardReceipt(eventId, collectorId, kind, amount, itemId))`. XP and Coins require a null item ID; Item, Artifact and Consumable require a nonempty ID of at most 128 characters. Team XP gives each currently connected participant the full amount in their own progression. Team pickup sharing applies only to Coins and Consumable; Item (including weapons/unlocks) and Artifact remain personal. Personal XP can be collected independently by multiple players using the same event ID. A team event is consumed globally once, and its collector, payload, recipients and per-recipient receipt bytes are frozen. Conflicting retries fail before enqueue; retry after partial enqueue only attempts the original not-yet-enqueued plans. There is no rerouting to later arrivals. Event and collection ledgers each fail closed at 100,000 without eviction. Each recipient drains `Rewards` and can inspect `ReceivedRewards`; XP is also applied to its local `Progression`. The client store and XP receipt sets are capped at 100,000; local and network XP sources must use noncolliding receipt IDs. Neither this store nor its item/artifact receipts changes an actual game inventory.

Rewards are not world drops: spawning private visible loot, pickup ownership/range checks, actual XP/item application, reconnect replay, acknowledgment and durable persistence are not implemented. A successful publish means queued, not delivered or acknowledged; disconnection can lose queued/in-flight receipts, so callers must not treat it as exactly-once delivery. Each peer has a separate ordered 128-frame control queue and one replaceable pending snapshot. Control overflow closes that peer and throws; client notification-channel overflow closes the client with an error and keeps the accepted receipt in its in-memory store. Drain `Rewards` promptly and handle errors on both channels. Other peers remain isolated.

Each client owns a distinct in-memory `Progression`: `ApplyXp(receiptId, recipientId, amount)` remains available for local sources, and `ChooseUpgrade(level, choice)` records a personal selection after the game determines eligibility. There is no shared XP total, persistence, or level calculation. Receipt tracking fails closed after 100,000 unique receipts instead of evicting replay protection.

Dispose host and clients with `await using`. Frames are big-endian 32-bit length-prefixed UTF-8 JSON, limited to 262,144 bytes. After the handshake both peers independently send nonce-correlated ping/pong heartbeats on a real-time 5-second interval. Accept, receive and heartbeat loops run on background tasks rather than the caller's UI/game synchronization context, independently of gameplay, menus or simulation ticks. Only the matching pong satisfies each outstanding ping; missing responses close the connection after at most 30 seconds from the ping attempt, even if unrelated traffic continues. Frame reads and writes, connection and handshake retain their 30-second deadlines; an incomplete frame or blocked write can therefore close a connection sooner. Heartbeats are handled internally, not delivered on game channels. At most one ping is outstanding per peer; heartbeat frames share the serialized send lock without bypassing framing. Protocol version 4 is incompatible with older peers. Version is `SessionHost.ProtocolVersion`.

**Security:** The password is transmitted in cleartext. There is no TLS, encryption, peer identity verification, replay protection for network commands, or protection from an observer/injector on the network. Use only a trusted LAN or an appropriately secured VPN; never expose the port directly to the internet. A password is an admission check, not secure authentication. Do not use valuable or reused passwords.

## Prototype operating limits

Snapshots must use strictly increasing ticks; host capture, serialization and fan-out are serialized across publishers. A stale tick is rejected. Cancellation or frame validation failure before fan-out does not advance the accepted tick. Snapshot and reward delivery remain queued-only, not acknowledged; neither reconnect replay nor durable run reconnection is implemented.

## Verification

`dotnet run --project tests/Wsm.Core.Tests/Wsm.Core.Tests.csproj` from the repository root executes the console harness against actual loopback TCP. It is not a Unity, IL2CPP, gameplay, VPN, or cross-machine integration test.
